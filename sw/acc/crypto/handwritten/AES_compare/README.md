# AES_compare: three-way AES-128 cycle comparison

Last updated: 2026-10-18: which KATs run the measured code; the two checks kept in AES_ext and AES_table.

Measurement rig, no assembly of its own. It drives the three AES-128
implementations, **ISE** (`bn.aes128`, `AES_ext/`), **compute-GF**
(`bn.gfmul.8`, `AES_gf/`) and **T-table** (`AES_table/`), through one fixed
procedure so the numbers are reproducible. Plain AES; key schedule measured
separately from encryption, with round keys already available to the encryption driver.
UOV kernels use different key-schedule strategies.

## Files
| file | role |
|---|---|
| `run_aes_compare.py` | the rig: builds the 11 ELFs (6 op drivers + 5 baselines), runs each on ACCSim, subtracts, prints the tables. Docstring records the method |
| `aes_compare.csv` | generated by the rig: regenerate, never hand-edit. One row per (variant, op): op cycles, setup cycles, cycles/byte, commit anchor |

## Test
```
python3 sw/acc/crypto/handwritten/AES_compare/run_aes_compare.py
```
No KAT and no bazel test here: this rig reports cycles, not correctness. The UOV KATs run the code it measures: the
`bn.aes128` instructions in every bngfaes and bnaesonly kernel, the compute-GF AES (comments aside) in the Is verify
bngfonly kernels, the T-table table and encrypt in the sw kernels and its key schedule as the per-op copies (same code, separate files).
`AES_ext/test_scripts/verify_aes128_mem.py` and `AES_table/test_scripts/verify_aes128_table.py` check the memory library
and the table on their own.

## Notes
- Every number is **op-driver run - setup-only baseline run**; each baseline is its driver minus exactly the measured op, so the subtraction strips the fixed operand/constant loading. Setup is a separate 7-40 cyc per call site (CSV `setup_cycles`).
- Results, ACCSim, 2026-07-22 at `6382387d78-dirty`. Key schedule: ISE 10, compute-GF 731, T-table 492 cyc. Encrypt: ISE 11 cyc / 32 B, compute-GF 923 cyc / 32 B, T-table 1147 cyc / 16 B, that is 0.34 / 28.8 / 71.7 cyc per byte.
- Work units differ: ISE and compute-GF do a 256-bit dual-block per call, the T-table a single 16 B block on 32-bit GPRs. Compare on cycles per byte and state the datapath width: the ISE-vs-T-table gap bundles round specialization, datapath width and `encz.swap`.
- The T-table costs 4 KiB of constants and does data-dependent loads, so it is not side-channel-equivalent.
- The ISE and compute-GF drivers measured here are standalone. The T-table files are shared: UOV
  kernels link `AES_table:aes128_table`, and through aliases `aes_encrypt` and `aes128table_352`;
  other kernels carry their own AES leaves.
